# PTCamBridge

Baballonia / Project Babble 系の口トラッキングカメラを、PaperTracker クライアントが期待する
MJPEG over HTTP ストリームとしてローカルホストに再配信する Windows 常駐ブリッジです。

公式 ESP32 カメラを持っていなくても、手持ちの UVC カメラ・有線 Babble ボード・WiFi MJPEG カメラを
PaperTracker の推論・OSC 送信機能に接続できます。

映像の推論やパラメータ変換は行いません。それは PaperTracker クライアント側の責務です。

## 仕組み

```
UVC カメラ ──(ffmpeg 子プロセス)──┐
有線ボード ──(シリアル/ETVR)─────┤──▶ FrameHub ──▶ HTTP MJPEG サーバー ──▶ PaperTracker
WiFi カメラ ─(MJPEG プロキシ)─────┘   (latest-frame-wins)   127.0.0.1:18080
```

フレームの配送は latest-frame-wins です。クライアントがフレーム 1 枚分でも遅れた場合、
溜め込むのではなく古いフレームを捨てて常に最新を配信します。口トラッキング用途では
遅延がフレームの網羅性より優先されるためです。変換 (回転・クロップ・再エンコード) の
手前でも同じ扱いをします。変換がカメラより遅いとドライバが送信でブロックし、その間
ソケットやシリアルの受信バッファに古い画像が溜まって遅延が増え続けるためです。

設計は Functional Core / Imperative Shell に従っています。プロトコルのパース・検証・
multipart エンコードは副作用のない純粋関数として `internal/core` に隔離してあり、
シリアル・プロセス・ソケット・ファイル I/O はすべてドライバ側に閉じ込めています。
おかげでワイヤーフォーマットの処理は実機なしで単体テストできます。

パッケージの分け方、依存の向き、コードを読む前に知っておくと迷わない設計判断は
[ARCHITECTURE.md](ARCHITECTURE.md) にまとめてあります。

## インストール

Windows 10 / 11 (x64) 向けの単一実行ファイルです。

1. `ptcambridge.exe` を任意のフォルダへ配置する
2. 実行するとタスクトレイに常駐する
3. UVC カメラを使う場合は ffmpeg を用意する (下記)
4. **使うカメラを設定する**

初回起動時に `%APPDATA%\PTCamBridge\ptcambridge.toml` が既定値で生成されます。
**この時点ではまだ映像は流れません。** 既定は UVC ですがカメラ名が空なので、
`uvc: no camera configured` で止まります。推測できる既定値が無いためで、
次のように設定してください。

```
ptcambridge.exe -list-devices
```

で出た名前を、生成された設定ファイルの `[source.uvc] device` に書きます
(トレイの「Edit settings」で開けます)。有線ボードや WiFi カメラを使う場合は
`[source] type` を `"serial"` / `"mjpeg"` に変えてください。

### PaperBridge (v0.1.x) からの移行

アプリ名を PTCamBridge に統一したため、名前を持つものはすべて変わりました。
**旧バージョンの設定・データは引き継ぎません。** 自動移行は入れていないので、
必要なものは手で移してください。

| 旧 | 新 |
|---|---|
| `%APPDATA%\PaperBridge\` | `%APPDATA%\PTCamBridge\` |
| `paperbridge.toml` | `ptcambridge.toml` |
| `paperbridge.log` | `ptcambridge.log` |
| `PAPERBRIDGE_*` 環境変数 | `PTCAMBRIDGE_*` |
| レジストリ `Run\PaperBridge` | `Run\PTCamBridge` |
| `wifi_cache.txt.paperbridge-backup` | `wifi_cache.txt.ptcambridge-backup` |
| multipart boundary の既定値 `paperbridge` | `ptcambridge` |

手順は次のとおりです。以下の `旧exe` は、お使いの旧バージョンの実行ファイル名に
読み替えてください。リリースからダウンロードしたものは
`paperbridge-windows-amd64-0.1.1.exe` のようにバージョンが付いた名前です。

1. **旧バージョンを終了する** (トレイアイコンから Quit)。
   常駐したままだと 5 のフォルダ削除が失敗し (Windows が実行中の exe をロックします)、
   新バージョンも既定ポートを取れずに起動できません
2. **`旧exe -restore-cache` を実行する。**
   `write_cache` を使っていた場合、これを先にやらないと PaperTracker 側に残った
   `wifi_cache.txt.paperbridge-backup` は新バージョンからは見えず、クライアントが
   ブリッジを指したまま戻せなくなります
3. 旧バージョンで自動起動を登録していた場合は `旧exe -uninstall-autostart`
   を実行する (レジストリのエントリ名が変わるため、残すと存在しない exe を指し続けます)
4. 引き継ぐものがあれば手で移す
   - 設定: `%APPDATA%\PaperBridge\paperbridge.toml` →
     `%APPDATA%\PTCamBridge\ptcambridge.toml`
     (**一般的な UVC カメラを使っている場合は、移した後に `[source.uvc]` の
     `size` を空、`framerate` を 0 にしてください。**
     旧バージョンの既定値 `240x240` / `30` はそのカメラには無いモードなので、
     残したままだとカメラが開きません → [解像度とフレームレート](#解像度とフレームレート))
   - 取得済み ffmpeg: `%APPDATA%\PaperBridge\bin\` → `%APPDATA%\PTCamBridge\bin\`
     (100 MB 超の再ダウンロードを避けるため。移さなければトレイから取り直せます)
5. `%APPDATA%\PaperBridge\` と旧 exe を削除する

`server.boundary` を明示的に設定している場合、その値は変わりません。既定値のまま
使っている場合はストリームの boundary 文字列が変わりますが、PaperTracker
クライアントは boundary を `--` の探索で見つけるため影響ありません。

### ffmpeg (UVC カメラを使う場合のみ)

有線 Babble ボードと WiFi MJPEG カメラだけを使うなら不要です。UVC カメラ
(USB ウェブカメラ) は ffmpeg を子プロセスとして起動して取り込むため、
ffmpeg が要ります。用意する方法は 2 つあります。

- **トレイメニューの「Get ffmpeg」** — 配布元・サイズ・ライセンスを確認する
  ダイアログが出て、同意すると発行元 (BtbN/FFmpeg-Builds) から直接ダウンロードし、
  `%APPDATA%\PTCamBridge\bin\ffmpeg.exe` に配置します。ダウンロード内容は
  SHA-256 で検証します。
- **自分で用意する** — `ptcambridge.exe` と同じフォルダに `ffmpeg.exe` を置くか、
  PATH に通すか、`[source.uvc] ffmpeg_path` でパスを指定します。

探索順は `ffmpeg_path` → 実行ファイルと同じフォルダ → PATH → 取得した ffmpeg
です。取得したものが最後なのは、ユーザーが明示的に指定した ffmpeg を、
トレイのクリック一つで黙って置き換えないためです。

**同梱していない理由**: PTCamBridge は ffmpeg をライブラリとしてリンクせず
別プロセスとして起動するため、同梱の有無に関わらず PTCamBridge 自身のライセンス
(MIT) には影響しません。一方で同梱すると、(1) LGPL バイナリの再配布者として
対応ソースの入手手段を提供し続ける義務が生じ、(2) ffmpeg を必要としない
シリアル / MJPEG 利用者にも 100 MB 超のダウンロードを強いることになります。
ユーザーの機器が発行元から直接受け取る形なら、どちらも発生しません。

## 使い方

### 1. カメラを選ぶ

利用可能なデバイスを一覧します。

```
ptcambridge.exe -list-devices
```

設定ファイルの `[source]` セクション、またはトレイメニューの「Source」から選択します。

| ソース | 対象 | 設定 |
|---|---|---|
| `uvc` | USB ウェブカメラ全般 | `[source.uvc] device` に DirectShow のデバイス名 |
| `serial` | 有線 Babble ボード / OpenIris 系 | `[source.serial] port`。`auto` で VID から自動探索 |
| `mjpeg` | WiFi ESP32 など HTTP 配信カメラ | `[source.mjpeg] url` |

#### 解像度とフレームレート

`[source.uvc] size` と `framerate` の既定は**空と 0、つまりカメラ任せ**です。

**カメラが持っていないモードを指定すると、そのカメラは一切開きません。** DirectShow は
要求した組み合わせが無いと `Could not set video options` で入力を開けず、再試行しても
毎回同じ場所で落ちます。こちらで値を決めないでおけば、カメラは自分の既定モードを選び、
それはどのカメラにも必ず存在します。

> **既に設定ファイルがある場合は、この既定は適用されません。**
>
> 既定が変わるのは、設定ファイルが新しく作られるときだけです。以前のバージョンが
> 作ったファイルには `size = "240x240"` と `framerate = 30` が**書かれた状態で残る**ので、
> 一般的な UVC カメラを使っていると、更新しても同じ理由で開けないままです。
>
> ログに `Could not set video options` が出ているなら、設定ファイルの該当行を
> 手で書き換えてください。
>
> ```toml
> [source.uvc]
> size = ""
> framerate = 0
> ```
>
> 自動では書き換えません。`240x240` が書いてあっても、それが「旧既定値のまま」なのか
> 「Babble ボードのために自分で選んだ値」なのかを、こちらから見分ける方法がないためです。
> 後者を黙って消すと、動いていた人の設定を壊します。

Babble や EyeTrackVR のボードを使う場合は明示してください。

```toml
[source.uvc]
device = "Bigeye"
size = "240x240"
framerate = 30
```

**自分のカメラが持っているモードは、`-list-devices` が並べます。**

```
ptcambridge.exe -list-devices
```

```
Capture devices:
  Bigeye
    @device_pnp_\\?\usb#vid_1234...
      1280x720 @ 5-30fps (mjpeg)
      640x480 @ 5-30fps (yuyv422)
```

**この一覧はカメラが申告したままなので、そのまま書き写せるとは限りません。**
`size` は `1280x720` のような 1 つの大きさ、`framerate` は整数です。

- `640x480 @ 5-30fps` — `size = "640x480"`、`framerate` は 5〜30 の整数
- `160x120-1280x720 @ 5-30fps` — **幅で答えるカメラ**です。`size` にはその間の
  1 つを書きます (`640x480` など)。範囲をそのまま書くことはできません
- `640x480 @ 29.97fps` — **書ける整数がありません**。`framerate = 0`
  (カメラ任せ) にしてください。30 と書くと、そのカメラは持っていない値を
  要求することになります

設定画面の候補欄には、書ける値だけが出ます。

**設定画面でも同じ一覧が候補に出ます。** カメラ名を入れると、その 1 台について
解像度とフレームレートの候補が埋まります。読みに行くのはカメラ名が決まったときだけで、
デバイス一覧と一緒には取りません — モードを調べるにはカメラを開く必要があり、
「どんなカメラがあるか」を見るたびに全カメラを掴みに行くわけにはいかないためです。

**今このアプリが使っているカメラは、一度調べた答えから返します。** UVC のカメラは
排他的なので、こちらが掴んでいる間はモードを調べるためにも開けません。一度でも
調べられていればそれで答えますが、まだ一度も調べていないカメラなら、その旨を
画面に出します。トレイの「一時停止」でカメラを解放すると調べられます。

**カメラを差し替えたときは、設定画面がそれに気づきます。** 同じフレンドリ名の別機種に
差し替えられても名前は変わらないので、名前を見ていても気づけません。代わりに見るのは
**キャプチャの様子**で、画面は状態を 2 秒ごとに読んでいます。合図は 3 つあります。

- **切れた。** 差し替えれば、そのカメラを掴んでいたドライバは必ず一度切れます
- **繋がった。** 抜いてから挿すまでの間に数え直しても、そこには**まだ新しいカメラが
  いません**。切れたことだけを合図にすると、その一覧で終わってしまいます
- **一時停止から戻った。** 止めている間の差し替えでは、ドライバは命じられて止まって
  いるので、切れたことになりません

合図があったらカメラの顔ぶれを数え直し、数えられたときだけ候補を捨てて訊き直します。
ブリッジが入れ替わりを知るのは顔ぶれを数えたときだけなので
(`forgetModesIfCamerasChanged`)、画面を開いたままだとその機会が来ないためです。
**列挙そのものが失敗したときは捨てません** — そのときはブリッジも素性を照らし
合わせないので、訊き直しても返るのは同じ古い憶えです。

見るのは**いま動いているソース**です。画面のラジオはまだ保存していない選択であり得る
ので、それで判断すると、シリアルが動いている画面で UVC を選んだまま置いておくだけで、
シリアルの再接続のたびにカメラの列挙が始まります。走っている数え直しに重ねることも
しません (重ねれば ffmpeg が積み上がります) が、その間に来た合図は**繰り越して**
1 回だけやり直します — 数え直しの最中に切れることこそ、まさに起きることだからです。

**モードが合っていなくて開けなかったときは、エラーがそのカメラの持ち物を添えます。**

```
uvc: ffmpeg closed its output (ffmpeg: Could not set video options ...);
  Bigeye offers 1280x720 @ 5-30fps (mjpeg), 640x480 @ 5-30fps (yuyv422)
```

ログを読むだけで次の一手が分かるようにするためです。調べるのは 1 回だけで、
再接続のたびには調べ直しません。

正方形が欲しいだけなら、カメラのモードを指定せずに `[transform] crop_square = true` で
切り出す手もあります。

UVC はまずカメラ自身に MJPEG を要求してパススルーします。1 フレームも得られず、
かつ ffmpeg の診断がデバイス未オープンを示していない場合は、再エンコードに切り替えて
試します。それでも 1 フレームも得られなければ「形式ではなくデバイスの問題だった」と
判断してパススルーへ戻します。デバイス使用中や起動直後の遅延も同じように失敗するため、
その一度の失敗でプロセスの残りすべてのフレームを再エンコード (CPU 増・画質劣化) に
落とさないためです。

再エンコードでフレームが得られた場合も、その時点では確定しません。パススルー試行時に
使用中だったカメラが、再エンコード試行までに解放されていた可能性があるためです。次の
試行でもう一度パススルーを試し、動作が確認できたデバイスに対して再び失敗した場合に
「このカメラは MJPEG を持たない」と確定します。確定後はパススルーを試しません。
本当に MJPEG 非対応のカメラでは、最初の切断後に 1 回だけ余分な試行が入ります。

`port = 'auto'` は既知の VID を持つポートを順に試します。同じ VID の別デバイスが
刺さっていても先頭で止まらず、再接続のたびに次の候補へ移ります。一度フレームを
返したポートは、切断後の 1 回だけ優先して開き直します。

**既知の VID が 1 つも無く、ポートが 1 本だけのときは、それを推測で開きます。**
ただし試すのは 3 回までです。既知の VID に載っていないだけの本物のボードはあり得ますし、
起動が遅いボードは最初の 5 秒では何も出さないので、数回は試します。それでもフレームが
来なければ、そのポートを開くのはやめます。

```
serial: no port matched a known camera vendor ID; set source.serial.port explicitly
  (COM4, 28DE:2102 USB シリアル デバイス, was opened 3 times and produced no frames,
   so it is not being opened again)
```

推測が外れているのに開き続けると、**そのデバイスを使う別のソフトがポートを取れなく
なり得ます**。実際に踏んだ例では、開いていたのは VR 機器 (Valve の `28DE:2102`) でした。

**やめるのは「開くこと」だけで、「待つこと」ではありません。** 再試行は続くので、
後から本物のボードを挿せば、次の試行が既知の VID として拾います。アプリを再起動する
必要はありません。1 枚でもフレームを返したポートは推測ではなくなるので、回数の
数え直しになります。

#### シリアルがつながらないとき

ポートは開けるのにフレームが来ない場合、ログは受信バイト数まで報告します。

```
serial: COM4 produced no frame for 5s (0 bytes received in that time)
```

- **0 バイト** — ボードが何も送っていません。有線ストリーミングモードになっているか
  (WiFi モードのままではないか) を確認してください
- **0 バイトではない** — バイトは届いているのにパケットが組み立てられていません。
  この場合は届いた先頭 16 バイトと、探している preamble が警告として出ます

```
level=WARN msg="bytes are arriving on the serial port but no packet matched; ..."
  port=COM4 baud=3000000 expected_header="ff a0 ff a1" first_bytes="ff a0 ff b1 10 00 ..."
```

`first_bytes` に規則的な preamble が見えるなら firmware のヘッダ違いなので、
`[source.serial] header` を実際の値に合わせれば通ります。まったく規則性が無い
場合はボーレート不一致を疑ってください (`[source.serial] baud`)。

同じ内容の警告は繰り返しません。再接続のたびに出ると埋もれるためで、届くバイトが
変わったときだけ改めて警告します。ただしポートあたり 3 通りまでです。流し続けている
デバイスは開くたびに合流位置が変わって先頭バイトも変わるため、変化のたびに警告して
いては結局埋もれるためです。抑止された分は debug レベルに出ます。

そのポートが一度でもフレームを返すと記録は消えるので、動いたあとに再び壊れた場合は
改めて警告します。

### 2. PaperTracker から接続する

PaperTracker クライアントはシリアル未接続時、実行ファイルと同じフォルダの
`wifi_cache.txt` に保存されたアドレスへ接続します。設定でインストールフォルダを
指定しておくと、起動時にこれを自動で書き換えます。

```toml
[papertracker]
install_dir = 'C:\Program Files\PaperTracker'
write_cache = true
```

元の内容は `wifi_cache.txt.ptcambridge-backup` へ退避します。退避は初回のみです
(毎回取り直すとバックアップがブリッジ自身のアドレスで上書きされ、
本来戻したい値が失われるため)。

退避先の名前に PTCamBridge が入っているのは意図的です。復元は `write_cache` が
false の起動ごとに走り、設定に無ければフォルダも自動探索するため、`.bak` のような
一般的な名前だと、別の何かが置いたファイルを読み戻して現在のキャッシュを壊し、
そのファイルまで消してしまいます。

`write_cache` を `false` に戻して起動すると、退避した内容を書き戻します。復元は
`install_dir` が指すフォルダに加えて、退避ファイルを持つ候補フォルダ**すべて**を
対象にします。`write_cache=true` のままクライアントを別の場所へ入れ直して
`install_dir` を更新すると、新旧どちらのフォルダにも退避ファイルが残るためです。
1 件で打ち切ると、もう一方のクライアントがブリッジを指したまま取り残されます。

自動探索は「PaperTracker らしいフォルダ」ではなく「PTCamBridge の退避ファイルが
あるフォルダ」を探します。インストールが複数ある環境で先頭の候補を選ぶと、何もして
いないフォルダに対して「戻すものはありません」と報告し、実際に書き換えたクライアントは
ブリッジを指したまま取り残されるためです。

キャッシュを書き換えたフォルダは、ブリッジ側の
`%APPDATA%\PTCamBridge\written-dirs.txt` に絶対パスで記録します
(`install_dir` に相対パスを書くと、起動時のカレントディレクトリ次第で別のフォルダを
指すためです)。`install_dir` に探索候補外の
フォルダ (ポータブル版など) を指定していた場合、`[papertracker]` セクションごと
削除するとそのフォルダを指すものが何も無くなり、復元先を見失うためです。この記録は
ブリッジの設定と同じ場所にあるので、設定フォルダごと手で削除すると失われます
(アンインストール前に `-restore-cache` を実行してください)。

`install_dir` の読み取りは設定ファイル全体の検証に依存しません。存在しないキーや
範囲外の値が含まれていてブリッジ自身は起動できない状態でも、フォルダ名は読めます。
アンインストール時に「変更していません」と言いながらクライアントがブリッジを
指したまま、という結果を避けるためです。`PTCAMBRIDGE_PAPERTRACKER_DIR` は通常起動と
同じくファイルより優先されます。この変数だけで指定されたフォルダも、ブリッジが
書き換えた以上は元に戻せる必要があるためです。

アンインストールする場合は設定ファイルごと消えて次回起動が来ないため、
`ptcambridge.exe -restore-cache` で明示的に戻してください。

`wifi_cache.txt` への書き込みと復元は、いずれも同じフォルダ内の一時ファイルへ
書いてから rename します。上書きの途中で失敗すると、クライアントの接続先が
空または半端な文字列になったまま残るためです (書き込み失敗はログに記録するだけで
起動は続くので、後から直す機会もありません)。

復元は、退避ファイルを `.restoring` を付けた名前へ移してから書き戻します。復元は
`write_cache=false` の起動ごとに走るため、二度実行されない形にする必要があります。
書き戻し後の削除に失敗して退避ファイルが残ると、次回起動時にまた書き戻され、
その間にクライアントが選び直したカメラのアドレスを消してしまいます。`.restoring`
のまま残っている場合、内容がキャッシュと一致していれば「片付けに失敗しただけ」と
判断して削除し、一致しなければ中断された復元としてログに記録します (自動では
適用しません)。`write_cache` を再び有効にすると、`.restoring` は退避ファイルとして
復帰し、次の復元で書き戻されます。

書き戻し自体に失敗した場合は、退避ファイルを元の名前へ戻してから終了します。書き戻し
前の失敗まで `.restoring` のままにすると、一時的な書き込み障害が「手作業でしか直せない
状態」になってしまうためです。元の名前に戻っていれば、次回起動でそのまま再試行されます。

書き戻しには成功したが削除だけ失敗した場合は、`.applied` を付けた名前へ変更します。
`.restoring` のまま残すと「書き戻し済み」と「書き戻し前に中断」が区別できず、その後
クライアントが別のカメラを選んでいると、`write_cache` を再有効化した際に古い値を
「クライアント本来のアドレス」として記録してしまうためです。`.applied` は次回の起動時に
削除され、退避ファイルとしては再利用されません。

手動で設定する場合は、クライアントの接続先を `127.0.0.1:18080` にしてください。

## 診断画面

トレイのアドレス項目 (`http://127.0.0.1:18080`) をクリックすると、ブラウザで
診断画面が開きます。映らないときに見る場所を 1 枚にまとめたものです。

- **状態** — ソース、受信中か再接続中か一時停止中か、稼働時間、直近のエラー
- **プレビュー** — 実際に届いている映像
- **フレーム** — 入力 fps、クライアント数、配信数、破棄数、フレームサイズ
- **デバイス** — 接続されているカメラとシリアルポートの名前。設定ファイルに
  書く名前はここから写せます
- **ffmpeg** — 導入済みか、どこにあるか
- **場所** — 設定ファイルとログフォルダのパス、バージョン

この画面は表示だけです。設定の変更は「設定」タブ (`/ui/settings`) で行います。
表示は PTCamBridge の表示言語に従います ([表示言語](#表示言語) を参照)。

プレビューが `/snapshot` を 1 枚ずつ取り直しているのは、`/stream` を使うと
この画面自身がクライアントとして数えられ、同じ画面が見せているクライアント数が
狂うためです。

デバイスの一覧は画面を開いたときに 1 度だけ取得します。Windows での列挙は
ffmpeg の起動を伴い最大 15 秒かかるので、繰り返しません。挿し直した後は
画面を再読み込みしてください。

## 設定画面

診断画面の「設定」タブ (`http://127.0.0.1:18080/ui/settings`) から、設定ファイルを
開かずに設定を変更できます。ソース、変換、配信、PaperTracker 連携、表示言語、ログ。

カメラ名とシリアルポート名は入力欄の候補に出るので、`-list-devices` を使わずに
選べます。UVC の欄には ffmpeg の取得ボタンもあります (トレイと同じく、配布元・URL・
サイズ・ライセンスを提示して同意を求めてから開始します)。

**「再起動が必要」の印が付いた設定** — 待受アドレス、PaperTracker 連携、表示言語、
ログ — は保存されますが、**効くのは次に起動したときからです**。保存後に画面が名前を
挙げて伝えます。これらは起動時にしか読まれないためです。たとえばトレイはメニューを
一度だけ、その時点の言語で組み立てるので、動作中に言語を切り替えても画面の言葉は
一つも変わりません。

設定ファイルを直接編集する方法は今までどおり有効です。画面に出していない項目
(`[source.serial] header`、`[server] extra_headers`、`[source] max_frame_size`) は
そちらで変更してください。画面から保存しても、これらは失われません。

保存するのは**画面上で実際に変更した項目だけ**です。土台には保存の直前に取り直した
設定を使うので、画面を開いたままトレイでソースを切り替えても、こちらの保存がそれを
元へ戻すことはありません。

画面に出していない項目もその土台に乗って往復するので、整数の設定には上限があります。
`source.max_frame_size`・`source.uvc.framerate`・`source.serial.baud` は
9007199254740991 (2^53 − 1) までです。設定画面は設定を JSON で読み書きし、JSON の数値は
倍精度浮動小数点なので、これを超える整数は読んだ時点で別の値になります。黙って丸めた値が
ファイルへ書き戻されるより、起動時に拒否する方が分かります。

## エンドポイント

| パス | 内容 |
|---|---|
| `/` および `/stream` | multipart MJPEG ストリーム |
| `/snapshot` | 最新フレーム 1 枚 (`image/jpeg`)。動作確認用 |
| `/healthz` | 200 / 503。フレームが届いている間だけ 200 |
| `/stats` | JSON。入力 fps、接続クライアント数、ドロップ数など |
| `/ui` | 診断画面 (下記) |
| `/ui/state` | JSON。診断画面が読む、表示用に整形済みの状態 |
| `/ui/settings` | 設定画面 (下記) |
| `/api/v1/config` | GET / PUT。設定の取得と適用。PUT の応答は動作中の設定で、起動時にしか読まれない設定を変更した場合は `pending_restart` にその名前が入る |
| `/api/v1/source` | POST `{"type":"uvc"}`。ソース切替 |
| `/api/v1/devices` | GET。カメラとシリアルポートの一覧 |
| `/api/v1/camera-modes?device=名前` | GET。そのカメラ 1 台が持っているモード |
| `/api/v1/ffmpeg` | GET。取得状況。POST。ffmpeg のダウンロード開始 (202) |

カメラとシリアルの列挙は独立して行い、失敗も `camera_error` / `serial_error`
として別々に返します。ffmpeg が無い環境でもシリアルポートは列挙できるので、
片方の失敗でもう片方の結果を捨てないためです。エラーが無く空の一覧は「何も
繋がっていない」、エラー付きの空の一覧は「分からない」を意味します。

ルート `/` でストリームを返すのは、クライアントがキャッシュしたアドレスを
パス指定なしで叩くためで、これが互換性要件の核心です。

管理 API (`/api/v1/*`) と診断画面 (`/ui`) は認証を持たないため、待受が
ループバック以外の場合は自動的に無効化されます。

ループバック待受は単独では防御になりません。ユーザーが開いた任意の Web ページは
`127.0.0.1` に到達でき、`text/plain` の POST であればプリフライトなしで送れるため、
管理 API は以下を満たさないリクエストを拒否します。

- `Host` がループバック名であること (DNS リバインディング対策)
- `Origin` ヘッダがある場合、それがループバックのページであること
- `Sec-Fetch-Site` ヘッダがある場合、`same-origin` または `none` であること
- ボディを伴うリクエストは `Content-Type: application/json` であること
  (これによりブラウザにプリフライトを強制し、上の `Origin` 検証で落とせます)

`Sec-Fetch-Site` を見るのは GET のためです。ページが
`<img src="http://127.0.0.1:18080/api/v1/devices">` のようにサブリソースとして
要求する場合、ブラウザは `Origin` を付けず、プリフライトも起きません。応答は
読めませんが、`/api/v1/devices` と `/api/v1/camera-modes` は Windows で ffmpeg を
起動して最大 15 秒待つため、URL を変えながら繰り返せばローカルにプロセスを作り続け
られます。後者は `device` を変えるだけで別の要求になるので、狙う側にとってはより
都合のよい的です。どちらも同じ `guardAdmin` を通ります。
`Sec-Fetch-Site` はページ側から偽装も抑止もできないため、これを送るブラウザは
この値で判定します。

`curl` やトレイのように `Origin` も `Sec-Fetch-*` も送らないクライアントは
そのまま利用できます。

変換を行わない既定設定でも、公開前に JPEG ヘッダの寸法を確認し、上限
(既定 16M ピクセル) を超えるフレームは破棄します。転送するだけならこちらは
デコードしませんが、デコードするのはクライアントであり、数百バイトのデータが
65535x65535 を宣言していればその割り当てを要求されるのはクライアント側だからです。
ヘッダの読み取りはキャプチャレートで実行できる程度に軽量です。

`server.extra_headers` に `Content-Type` と `Content-Length` は指定できません。
これらはエンコーダが自分で出力するため、同名ヘッダを重複させるとクライアントが
どちらを採用するかで multipart の同期が崩れます。

### ソース切替の判定

ソースを切り替えたとき、ブリッジは最初の 1 フレームが届くまで成功とみなしません。
ドライバは自力で再接続するため「まだ失敗していない」ことは何の保証にもならず、
フレームだけが動作の証拠だからです。届かなければ元のソースへ戻します。

上限は 30 秒です。初回試行を丸ごと含める必要があるためで、MJPEG なら
dial・TLS・ヘッダー・最初のフレームでそれぞれ 5 秒、UVC ならストール 10 秒 +
バックオフ + 再エンコードでの再試行 10 秒がかかりえます。動作するソースなら
フレームが届いた時点で即座に返るので、長くかかるのは失敗するときだけです。

判定は「Hub に公開されたフレーム」で行います。ドライバが JPEG を認識した時点
ではなく、変換まで通ってクライアントが実際に受け取れる状態になったことを確認
するためです。

要求した HTTP クライアントが切断・タイムアウトした場合は、その時点で確認を打ち
切って元のソースへ戻します。結果を受け取る相手がいない状態で切替を完了させると、
呼び出し側が失敗と認識した変更が動作中設定と設定ファイルに残るためです。ロック
待ちの間に要求が消えていた場合も、`server.*` だけの変更を含めて適用しません。

最初の 1 フレームは JPEG としてデコードできるかまで確認します。フレーム単位の
チェックは構造 (マーカー列) しか見ておらず、SOI と EOI だけのデータも通ってしま
うためです。これは「バイトが届いた」であって「ソースが動いている」ではないので、
可否を決める 1 枚だけは実際にデコードします。

このデコード確認は切替時だけでなく常に行われます。デコードできるフレームが 1 枚
届くまで Hub には何も公開しないので、起動時や再開時も「構造だけ正しいフレームを
送り続ける上流」が正常扱いになることはありません (Hub にフレームが無いため
`/healthz` は 503、トレイの fps も 0 のままです)。デコードできない間は
500ms 間隔で再確認し、その間のフレームは破棄します。毎フレームのデコードは
高すぎるためです。

一方、**起動時は「動作するまで待って打ち切る」ことはしません**。サインイン直後で
カメラがまだ接続されていない場合に打ち切ってしまうと、後から接続しても拾えなく
なるためです。起動時はドライバを再接続させ続け、状態は `/healthz` に出ます。

`server.*` だけを変更した場合はキャプチャを再起動しないので、この検証も走りま
せん。カメラが再接続中でも `hold_on_source_loss` などを変更できます。

ただしドライバが再試行では直らないエラー (MJPEG の 404 など) で停止している
場合は、同じソースを選び直すと再起動します。原因を取り除いた後に同じ設定を
選ぶのが復旧手段なので、設定が変わっていないことを理由に何もしないと 503 の
まま戻れなくなるためです。

一時停止中はソースを変更できません。何も起動できない以上、動作するかどうかを
確かめようがなく、確認せずに受け入れると動いていた設定を失うためです。再開時に
検証しないのは起動時と同じ理由 (後から接続されたカメラを拾う必要がある) です。
`server.*` の変更は一時停止中でも可能です。

### 再起動が必要な設定

`server.listen` にポート 0 は指定できません。起動ごとに別のポートが割り当てられる
ため、クライアントに書き込んだアドレスが次回には存在せず、bind による二重起動の
抑止 (ポートがこのアプリの識別子) も働かなくなるためです。`00`、`+0`、`127.0.0.1:`
のようにポート 0 と等価な表記も同様に拒否します。ポートはサービス名ではなく
1〜65535 の数値で指定してください (この値は他アプリの設定ファイルに書き込まれるため、
そちらでも同じ表記になる必要があります)。

`server.listen`、`log.*`、`papertracker.*`、`ui.language` はプロセス起動時にのみ
読まれます。`PUT /api/v1/config` でこれらを変更した場合、**設定としては受け入れて保存
しますが、この起動の振る舞いは変わりません**。応答の `pending_restart` にその名前が入る
ので、呼び出し側は「保存はされたが、効くのは次の起動から」と言えます。

黙って受け入れるだけにしないのは、設定を変えたのに何も変わらない理由が誰にも分からなく
なるためです。たとえばトレイはメニューを一度だけ、その時点の言語が与えたラベルで組み立てる
ので、動作中に `ui.language` を変えても画面上の言葉は一つも変わりません。

値そのものは据え置かずに受け入れます。据え置くと、動作中の設定とファイルの中身が食い
違ったまま、その差を覗く手段がどこにも無くなるためです。保存した値を確かめることも、
気が変わって元に戻すこともできません (取り消しの要求は「動作中の値」と同じなので変更と
して現れず、ファイルに入ったままの値が書き直されるだけになります)。

起動時にコマンドラインや環境変数で上書きした設定 (`-log-level`、`PTCAMBRIDGE_LANGUAGE`
など) は `pending_restart` に含めません。ファイルに何を書いても次の起動でも同じ上書きが
勝つので、それを保留と呼ぶと起きない変更を知らせ続けることになります。設定画面は
これらを別に挙げて「ここで変えても反映されません」と伝えます。

上書きされたかどうかは、**指定されたかどうか**で数えます。値がファイルと同じでも上書きは
上書きです。`PTCAMBRIDGE_LANGUAGE=en` をファイルの `en` に重ねた場合、値はどこも動きま
せんが、ファイルを `ja` に書き換えても次の起動はやはり `en` です。

数えるのは**環境変数だけ**で、コマンドラインのフラグは数えません。フラグはこの起動だけの
ものだからです。自動起動が登録するのは実行ファイルと `-config` だけなので、
`-log-level debug` で一度起動した人が設定画面から `info` を保存すれば、それは次の
サインインで実際に効きます。`pending_restart` はそのとおり `log.level` を挙げます。

`pending_restart` の名前は葉ごと (`papertracker.install_dir`、`papertracker.write_cache`)
です。まとめると、上書きされた葉を差し引くときに隣の正当な保留まで消えます。`install_dir`
だけを環境変数で指定している機械で `write_cache` を変えると、次の起動では確かに
`write_cache` が変わるのに、名前が 1 つしかなければそれも黙ることになります。

`pending_restart` は応答にのみ現れますが、`PUT` の本体に含まれていても受け付けます
(値は読みません)。応答をそのまま送り返す呼び出し側が、自分では付けていない項目のせいで
400 を受け取るのは往復として筋が通らないためです。設定として知らない項目は今までどおり
撥ねます。

`server.boundary`、`server.extra_headers`、`server.hold_on_source_loss` は
再起動なしで反映されます。接続中のクライアントは開始時の書式のまま維持され、
以降の新規接続から新しい書式になります。

設定の適用には成功したがファイルへの保存に失敗した場合は 500 を返します。
このとき変更自体は動作中の設定に反映されていますが、再起動すると失われます。

保存の直前に設定ファイルを読み直し、その内容へ変更分を重ねます。実行中に
「Edit settings」でファイルを直接編集しても、その後トレイで別の項目を変更した
ときに上書きで消えることはありません。`server.extra_headers` はキー単位で
マージします。テーブル全体を 1 つの値として置き換えると、API 経由で別のヘッダを
変更しただけで、ファイルに手で追加したヘッダが消えてしまうためです
(呼び出し側が削除したキーは、そのキーへの変更として削除されます)。

読み直した内容が TOML として壊れている場合 (編集途中など) は保存を行わず、
500 と共に保留にします。編集中のファイルを古い内容で置き換えないためです。
ファイルが読める状態に戻れば、次回の保存で保留分ごと書き込まれます。

保存できなかった内容はブリッジ側で保留され、次に保存が成功したときに一緒に書き
込まれます。同じ設定をそのまま再送するだけで再試行になります (動作中の設定とは
差分が無くても、保留分が書かれます)。**この再試行は、ソースが起動できない状態でも
働きます。** 書けなかった保存は、それを生んだ前の変更のものであって、再送そのものの
成否とは関係が無いためです。動作中のブリッジは既にその値で動いている
ので、書き込めるようになった時点でファイルを実態に合わせます。

## 設定

`%APPDATA%\PTCamBridge\ptcambridge.toml`。初回起動時に
[`internal/config/default.toml`](internal/config/default.toml) がそのまま書き出されます。
各項目の説明はコメントとして入っているので、生成されたファイルをそのまま読めます
(リポジトリ側と中身が同一であることはテストで保証しています)。

ただしトレイや管理 API から設定を変更すると、そのタイミングで設定内容だけが
書き直され、コメントは失われます。設定の表現を 1 つに保つためで、その頃には
説明としての役目は終わっているという判断です。

優先順位はコマンドライン引数 > 環境変数 (`PTCAMBRIDGE_*`) > 設定ファイル > 既定値です。

### 表示言語

```toml
[ui]
language = "auto"   # "auto" | "en" | "ja"
```

`auto` は OS の表示言語に従います (Windows は `GetUserPreferredUILanguages`、
それ以外は `LC_ALL` / `LC_MESSAGES` / `LANG`)。Windows で見るのは表示言語であって
地域形式ではないので、`auto` の結果を変えたい場合は地域設定ではなく表示言語を
変更してください。Windows でも環境変数があれば
そちらを優先するので、システム設定を変えずに切り替えて試せます。
`PTCAMBRIDGE_LANGUAGE=ja` でも指定できます。

この設定は起動時にのみ読みます。トレイのメニューは起動時に一度だけ組み立てるため、
管理 API から変更しても画面は変わりません (`server.listen` や `log.level` と同じ
扱いで、実行中の変更は拒否します)。

対象はトレイのメニューと確認ダイアログ、`-list-devices` と `-restore-cache` の出力、
それと**ユーザーが対処できる少数のエラー** (カメラ未設定、ffmpeg 未検出、
カメラボードらしいシリアルポートが無い) です。起動時のエラー (`ptcambridge: ...`)
は英語のままで、これはログと同じ扱いです。

**ログは常に英語です。** 不具合報告にそのまま貼れること、文言で検索できることを
優先しました。同じ理由で `/stats` や `/api/v1/*` の応答も英語のままです
(こちらはプログラムが読むものなので、安定していることが重要です)。

対処できないエラー (ポートのアクセス拒否、途中で消えたカメラなど) も英語のまま
トレイに出ます。それらはドライバが書いた詳細そのものに価値があり、翻訳した要約に
置き換えると情報が減るためです。`jp` のような未知の値は起動時にエラーで拒否します
(黙って英語のままだと、設定が効かないのか綴りが違うのか分からないためです)。

存在しないキーが書かれている場合はエラーで起動を中止します。`lsiten` のような
綴り間違いが黙って既定値で起動し、意図しないアドレスやソースで動くのを防ぐため
です。`PUT /api/v1/config` も同様に未知のフィールドを 400 で拒否します。

環境変数の値が解釈できない場合 (`PTCAMBRIDGE_SERIAL_BAUD=abc` など) も起動を中止
します。黙って無視するとファイル側の値で起動してしまい、変数を設定したつもりの
利用者には別の設定で動いていることが分かりません。

コマンドライン引数と環境変数で上書きした値は設定ファイルへ書き戻されません。
トレイなどで別の項目を変更しても、`-device` や `PTCAMBRIDGE_*` のような一時的な
指定が恒久化することはありません。

主なコマンドライン引数:

```
-config <path>            設定ファイルを指定
-listen <host:port>        待受アドレスを上書き
-source <uvc|serial|mjpeg> ソース種別を上書き
-device <name>             UVC デバイス名を上書き
-headless                  トレイなしで起動
-console                   ログを標準エラー出力にも出す
-list-devices              デバイス一覧を表示して終了
-install-autostart         サインイン時の自動起動を登録して終了
-restore-cache             PaperTracker の接続先を元に戻して終了
```

`-config` を併せて指定して `-install-autostart` した場合、その設定ファイルのパスも
Run キーに記録されます。次回サインイン時に既定の `%APPDATA%` 側へ戻ってしまい、
意図しないソースやポートで起動するのを防ぐためです。

## 制約

UVC デバイスは排他アクセスです。PTCamBridge が掴んでいる間、同じカメラを
Baballonia 本体から開くことはできません。切り替えて使う想定であり、
同時利用は保証しません。トレイメニューの「Pause」でカメラを解放できます。

MJPEG ソースについては、上流のファームウェアが HTTP の多重接続に対応していれば
併用できる可能性があります。

## ビルド

```
go test ./...
GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build -o ptcambridge.exe ./cmd/ptcambridge
```

cgo は使いません。Windows でのカメラ取得は ffmpeg を子プロセスとして起動し
stdout から MJPEG を読む方式で解決しているため、`CGO_ENABLED=0` の単一バイナリを維持できます。

配布用の exe はさらに `-trimpath -ldflags "-s -w -H=windowsgui -X main.Version=<version>"`
を付けて作ります。`-H=windowsgui` はトレイ常駐アプリがコンソール窓を連れてこないため、
`-X main.Version` は `-version` と `/stats` が返す値を埋め込むためです。

## ビルドとリリース (GitHub Actions)

| ワークフロー | 起動条件 | 内容 |
| --- | --- | --- |
| `ci.yml` | `master` への push / PR | gofmt・vet (Linux/Windows 両 GOOS)・`go test -race`・Windows 向けビルド |
| `build.yml` | 手動 / `release.yml` から | テスト → バージョン入り単一 exe を発行 → Windows でスモークテスト |
| `release.yml` | バージョンタグの push | `build.yml` を呼び、成果物を GitHub Release へ添付 |

`build.yml` が発行する exe のファイル名にはバージョンが入ります
(`ptcambridge-windows-amd64-0.1.0.exe`)。Artifacts の名前も同じで、展開したあとの
exe 単体でもどのビルドか分かります。動作はファイル名に依存しません。

発行は Linux でのクロスコンパイル (`CGO_ENABLED=0`) で、`ci.yml` が全 push で
作っているものと同じ経路です。リリースのときだけ別の作り方をすると、CI が通っているのに
リリースだけ壊れる、という食い違いが起きるためです。

スモークテストは Windows ランナーで実際に exe を起動します。`-version` が正常終了すること、
`-headless` で常駐させて `/stats` が埋め込んだバージョンを返すこと、カメラ未接続なので
`/healthz` が 503 を返すことを確認します。バージョンの確認に標準出力を使わないのは、
`-H=windowsgui` の exe が親のコンソールに出力を渡せるかどうかが実行環境によるためで、
動いているプロセス自身に答えさせる方が確実だからです。

### 手動ビルド

公開リリースを作らずにリリース用の exe を得たい場合 (実機確認用など) は、
Actions → **Build** → Run workflow を実行し、完了後に Artifacts からダウンロードします。
`version` を省略すると `0.0.0` になります。

### リリース

バージョンのタグを push すると `release.yml` が動きます。接頭辞 `v` の有無はどちらでも構いません。

```bash
git tag 0.1.0
git push origin 0.1.0
```

GitHub の UI からリリースを作った場合もタグが作られるのでワークフローは動きます。
その場合はリリースが既に存在するため、**成果物の添付だけ**を行い、リリースノートは
上書きしません。

対応するタグ形式は `[v]MAJOR.MINOR.PATCH[-プレリリース識別子]` (例: `1.2.3`、`v1.2.3-rc.1`)。
プレリリース識別子を含むタグは、ワークフローが**リリースを新規作成する場合に限り**
prerelease として公開されます。ビルドメタデータ (`1.2.3+build.1`) を含むタグは、埋め込まれる
バージョンとタグが食い違ったまま公開されるのを避けるため、ワークフローの冒頭で拒否します。

リリース成果物は単一 exe だけで、`ffmpeg.exe` は含みません。CI でダウンロードして
成果物に混ぜることもしません。混ぜた時点でこのリポジトリが LGPL バイナリの再配布者に
なり、「インストール」の節に書いた同梱しない理由がそのまま成り立たなくなるためです。
